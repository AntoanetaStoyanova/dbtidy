# Spec — v0.3 : `convert`, du SQL legacy aux modèles dbt en couches

*Rédigé le : 9 octobre 2026*

> Spec provisoire jusqu'à la fin de l'étape 1 du plan (spike). Les décisions marquées *(à confirmer)* sont validées ou corrigées par le spike avant d'écrire le code de production.

## Contexte

La v0.2 vérifie des modèles dbt existants (`check`). La feuille de route ([roadmap-sql-oracle-dbt.md](roadmap-sql-oracle-dbt.md), section v0.3) prévoit l'étape suivante : partir d'une requête Oracle legacy et produire directement des modèles conformes aux conventions. Aujourd'hui, ce découpage se fait à la main. Il est long, répétitif et source d'erreurs : jointure laissée en staging, `NVL` et `(+)` recopiés tels quels.

## Objectif

`dbtidy convert requete.sql` lit une requête `SELECT` Oracle et écrit, dans les dossiers des couches définis par `dbtidy.yml` :

- un `_<source>__sources.yml` par source ;
- un modèle staging par table source ;
- des modèles intermediate pour les jointures, les CTE et la logique métier ;
- un modèle mart pour l'agrégation et le `SELECT` final.

Les modèles produits sont modernisés et passent `check`. Ce qui ne se convertit pas est marqué `-- TODO` au lieu d'être deviné.

## Périmètre

- Commande `dbtidy convert QUERY [--name NAME] [--rename ANCIEN=NOUVEAU ...] [--config PATH] [--force] [--dry-run]`.
- Entrée : un fichier contenant une seule requête `SELECT` (CTE comprises) en dialecte Oracle.
- Sources :
  - chaque table `SCHEMA.TABLE` devient une source dbt ;
  - le nom de la source vient du mapping `convert.sources` de `dbtidy.yml` (`ERP_PROD: erp`) ;
  - un fichier par source, `<dossier staging>/<source>/_<source>__sources.yml` (convention dbt Labs).
- Staging : un modèle `stg_<source>__<table>.sql` par table, dans `<dossier staging>/<source>/`. Il fait un `select` des seules colonnes utilisées par la requête, depuis `{{ source() }}`, avec les noms dans la casse de `columns_case`. Une table lue plusieurs fois (auto-jointure, CTE et requête principale) donne un seul staging, avec l'union des colonnes utilisées.
- Intermediate :
  - chaque CTE et chaque sous-requête du `FROM` devient un modèle `int_<nom>.sql`, avec son `GROUP BY` éventuel. Le nom est celui de la CTE ou l'alias de la sous-requête, sauf si `--rename` en donne un autre (`--rename t1=clients_actifs` → `int_clients_actifs.sql`) ;
  - si la requête principale contient une jointure, un `WHERE`, un alias ou de la logique métier qui ne dépend pas d'un agrégat, cette partie devient `int_<nom du mart sans préfixe>.sql`.
- Mart : le `GROUP BY`, le `HAVING`, le `DISTINCT`, ce qui dépend d'un agrégat et le `SELECT` final de la requête principale deviennent `fct_<nom>.sql`. Le nom est donné par `--name`, sinon déduit du fichier (`rapport_clients.sql` → `fct_rapport_clients`).
- Préfixes : `stg_`, `int_` et `fct_` sont les premiers préfixes de `config.layers` ; `--name` doit commencer par un préfixe mart de la configuration.
- La couche de chaque élément suit la section « Règles de découpage ».
- Liens : les tables et CTE sont remplacées par des `{{ ref() }}` vers les modèles générés.
- Modernisation des modèles générés :
  - `(+)` → `LEFT JOIN ... ON` ;
  - `NVL` → `COALESCE` ;
  - `DECODE` → `CASE`.
- Conservés tels quels : `GROUP BY`, fonctions analytiques (`OVER (...)`), jointures ANSI.
- Top N : `SELECT … FROM (SELECT … ORDER BY x) WHERE ROWNUM <= n` → `SELECT … ORDER BY x FETCH FIRST n ROWS ONLY`. `ROWNUM` et `ORDER BY` dans le même `SELECT` ne sont pas un top N (Oracle filtre avant de trier) : `-- TODO`.
- `-- TODO` en tête du modèle concerné, avec la raison, pour :
  - les sous-requêtes corrélées ;
  - `CONNECT BY` ;
  - `UNION`, `INTERSECT` et `MINUS` ;
  - `ROWNUM` hors du motif top N.

  Le fragment est recopié tel quel dans le modèle.
- Refus (exit 2), avec un message en français qui dit quoi corriger :
  - fichier qui n'est pas une requête `SELECT` (PL/SQL, `MERGE`, `INSERT`, plusieurs requêtes) ;
  - colonne sans préfixe de table dans un `SELECT` qui lit plusieurs tables, `SELECT *` ou `t.*` (liste des colonnes à préfixer ou à expliciter) ;
  - sous-requête du `FROM` sans alias ;
  - deux modèles générés de même nom dans une conversion (`--name fct_ca` et une CTE `ca`) : le message suggère `--rename` ;
  - nom de modèle plus long que `oracle.max_identifier_length` (dbt-oracle crée une vue de ce nom) : le message suggère `--rename` ou un nom de source plus court ;
  - `--name` sans préfixe mart de la configuration.
- Modèles existants :
  - un staging déjà présent est réutilisé (`ref()` dessus, fichier non modifié) s'il expose toutes les colonnes requises ; sinon exit 2 avec la liste des colonnes manquantes ;
  - un intermediate ou un mart déjà présent bloque la conversion (exit 2), sauf avec `--force` ;
  - un `_<source>__sources.yml` déjà présent est complété des tables manquantes ; ses commentaires sont perdus, ce qu'un avertissement signale.
- `--dry-run` : affiche les fichiers qui seraient écrits et leur contenu, sans rien écrire.
- Contrôle final : `check` est lancé sur les modèles générés, et le rapport est affiché.
- Preuve :
  - tests de structure : chaque modèle généré est relu par sqlglot après substitution du Jinja et passe `check` sans erreur ;
  - un corpus de 10 requêtes legacy dans `examples/legacy/`.
- Validation de bout en bout sur Oracle Free (Docker + `dbt-oracle`) : l'ancienne requête et les modèles générés donnent les mêmes lignes. Elle se fait dans une étape séparée, hors CI.
- Documentation Sphinx (`convert.rst`), README, `CHANGELOG.md` (0.3.0).

## Règles de découpage

L'outil est déterministe : chaque élément de la requête va dans une couche fixe. Quand un élément peut aller dans plusieurs couches, c'est sa position dans la requête d'origine qui décide.

| Élément | Où il se trouve | Couche |
| --- | --- | --- |
| Colonnes utilisées d'une table | partout | staging : `select` simple, un modèle par table |
| Casse des noms (`CLIENT_ID` → `client_id`) | partout | staging : seul changement autorisé, pour respecter `columns_case` |
| Alias de colonne (`AS ca`) | partout, hors agrégat | intermediate : c'est un renommage métier |
| `WHERE` | partout | intermediate : le staging garde toutes les lignes de la source |
| Jointure (ANSI ou `(+)`) | partout | intermediate |
| `CASE`, `DECODE`, `NVL`, calcul, fonction (`UPPER`, `TO_CHAR`…) | partout, hors agrégat | intermediate |
| Fonction analytique (`OVER`) | partout, hors agrégat | intermediate |
| Sous-requête non corrélée dans le `WHERE` ou le `SELECT` (`x IN (SELECT …)`) | partout | dans le modèle qui la contient ; ses tables deviennent des `ref()` vers le staging |
| CTE ou sous-requête du `FROM` | — | un `int_<nom>` chacune, avec tout son contenu |
| `GROUP BY`, `HAVING`, `DISTINCT` | CTE ou sous-requête | dans le `int_` de cette CTE (changement de grain) |
| `GROUP BY`, `HAVING`, `DISTINCT` | requête principale | mart |
| Ce qui porte sur un agrégat : alias, calcul, `OVER` (`SUM(x) AS total`, `RANK() OVER (ORDER BY SUM(x))`) | requête principale | mart, avec le `GROUP BY` |
| `SELECT` final | requête principale | mart : un seul mart par requête |
| Top N : `ROWNUM <= n` autour d'une sous-requête triée | partout | dans le modèle où il se trouve, réécrit en `ORDER BY ... FETCH FIRST n ROWS ONLY` |
| `ORDER BY` seul | CTE ou sous-requête | retiré, avec une note dans le modèle (une table n'a pas d'ordre) |
| `ORDER BY` seul | requête principale | conservé dans le mart |
| Autre usage de `ROWNUM` (même `SELECT` que l'`ORDER BY`, numérotation, `ROWNUM = 1`…) | partout | `-- TODO` |
| `CONNECT BY`, `UNION`/`INTERSECT`/`MINUS`, sous-requête corrélée | partout | `-- TODO`, fragment recopié |

Cas limites :

- **Requête principale sans élément intermediate** (pas de jointure, de `WHERE`, d'alias ni de logique) : on n'écrit pas d'intermediate vide. Le mart lit directement le staging ou le `int_` de la CTE avec `ref()`, et porte le `GROUP BY` éventuel.
- **Requête principale avec des éléments intermediate et des éléments mart** : `int_<nom du mart sans préfixe>` porte les jointures, le `WHERE` et la logique. Le mart lit ce modèle et porte le `GROUP BY`, le `HAVING`, le `DISTINCT` et l'`ORDER BY`.
- **Agrégat utilisé dans une expression** de la requête principale (`SUM(NVL(x, 0)) * 1.2 AS total`) : l'expression interne (`NVL`) va dans l'intermediate sous un alias, et l'agrégat avec le calcul et l'alias qui l'entourent va dans le mart.

Exemple :

```sql
WITH ca AS (
  SELECT client_id, SUM(montant) total FROM ventes.factures GROUP BY client_id
)
SELECT c.nom, ca.total FROM ventes.clients c JOIN ca ON c.id = ca.client_id
```

Ce que produit la conversion :
- `stg_ventes__factures` et `stg_ventes__clients` ;
- `int_ca`, qui porte le `GROUP BY` ;
- `int_<nom>`, qui porte la jointure ;
- le mart, qui ne fait que le `select` final.

## Hors périmètre

- PL/SQL, `MERGE`, `INSERT`, `UPDATE` et le DDL.
- Conversion des sous-requêtes corrélées, de `CONNECT BY` et des `UNION` (marqués `-- TODO` seulement).
- Compléter un staging existant avec des colonnes manquantes.
- `schema.yml` (documentation et tests des modèles générés).
- Modèles incrémentaux et `config()` de matérialisation.
- Choix automatique de `dim_` plutôt que `fct_` : le préfixe vient de `--name`.
- Plusieurs requêtes en une commande : un appel par fichier.
- Publication PyPI de la 0.3.0. Elle se fera après la validation Oracle, comme pour la 0.2.

## Décisions

| Sujet | Décision | Raison |
| --- | --- | --- |
| Couche de chaque élément | Fixée par la section « Règles de découpage » ; quand un élément peut aller dans plusieurs couches, sa position dans la requête décide | L'outil est déterministe : aucun cas ne doit être laissé à l'appréciation |
| Staging | Sélection des colonnes et casse des noms, rien d'autre | Choix de l'utilisatrice : aucune transformation en staging |
| `GROUP BY` en intermediate | Autorisé quand il est dans une CTE ou une sous-requête | Changement de grain (*re-graining*), un rôle de l'intermediate selon le guide dbt « How we structure our dbt projects » |
| Contenu du mart | `GROUP BY`, `HAVING`, `DISTINCT`, `ORDER BY`, ce qui porte sur un agrégat et `SELECT` final de la requête principale | Le mart expose le résultat final ; ce qui dépend d'un agrégat ne peut pas être calculé avant le `GROUP BY` |
| Intermediate vide | Pas écrit : le mart lit directement le staging | Pas de modèle qui ne fait rien |
| Top N | Seul le motif imbriqué `(SELECT … ORDER BY) WHERE ROWNUM <= n` → `FETCH FIRST n ROWS ONLY` ; `ROWNUM` et `ORDER BY` au même niveau → `-- TODO` | Au même niveau, Oracle filtre avant de trier : le réécrire changerait le résultat. `FETCH FIRST` existe à partir d'Oracle 12c |
| Colonnes ambiguës | Colonne sans préfixe quand le `SELECT` lit plusieurs tables, `*` ou `t.*` → exit 2 avec la liste à corriger | Sans schéma, on ne sait pas à quelle table appartient la colonne ; on ne devine pas |
| Organisation des sources | Par source : `<staging>/<source>/_<source>__sources.yml` et les `stg_` dans ce dossier | Convention dbt Labs |
| `_<source>__sources.yml` existant | Complété des tables manquantes, avec un avertissement (commentaires perdus à la réécriture YAML) | Évite une étape manuelle ; l'avertissement rend la perte visible |
| Staging existant incomplet | Exit 2 avec les colonnes manquantes | L'`int_` généré casserait au `dbt run` ; compléter le staging reste hors périmètre |
| Longueur des noms de modèles | Exit 2 au-delà de `oracle.max_identifier_length` | dbt-oracle crée une vue du nom du modèle |
| Préfixes | Premiers préfixes de `config.layers` ; `--name` sans préfixe mart → exit 2 | Les fichiers générés respectent NAM001 quelle que soit la configuration |
| Mapping schéma → source | `convert.sources: {ERP_PROD: erp}` dans `dbtidy.yml` | Réutilisable pour toutes les requêtes ; le schéma Oracle n'est pas déductible du nom métier |
| Table sans schéma ou schéma absent du mapping | Erreur exit 2 qui liste les schémas à ajouter *(à confirmer)* | Ne pas deviner un nom de source |
| Nom des fichiers staging | `stg_<source>__<table>` en minuscules | Convention dbt Labs, déjà utilisée dans les exemples |
| Nom du mart | `--name`, sinon `fct_` + nom du fichier | Choix de l'utilisatrice |
| Nom d'un intermediate | `int_<nom de la CTE ou alias de la sous-requête>`, ou `int_<nom du mart sans préfixe>` pour la requête principale | Lisible et sans collision dans une même conversion |
| Noms de CTE peu parlants (`t1`, `tmp`) | Option `--rename ANCIEN=NOUVEAU`, répétable ; les `ref()` suivent le nouveau nom | Déterministe ; évite de renommer les fichiers et les `ref()` à la main après coup |
| Collision entre deux conversions (`int_ca.sql` déjà présent) | Exit 2 sans `--force`, avec un message qui suggère `--rename` | Ne jamais écraser en silence |
| Collision dans une même conversion (`--name fct_ca` et CTE `ca`) | Exit 2, avec un message qui suggère `--rename` | Deux modèles ne peuvent pas porter le même nom |
| Sous-requête du `FROM` sans alias | Exit 2 | Pas de nom pour son `int_` |
| `--rename` invalide | Exit 2 si `ANCIEN` n'est ni une CTE ni un alias de sous-requête, ou si `NOUVEAU` n'est pas un identifiant valide | Une faute de frappe ne doit pas passer inaperçue |
| Colonnes du staging | Seulement celles utilisées par la requête, alias de table résolus | Feuille de route ; un staging minimal se relit facilement |
| Casse des colonnes | `columns_case` de la configuration, minuscules par défaut | Les modèles générés sont conformes à NAM002 |
| Staging existant | Réutilisé tel quel | Le compléter automatiquement est trop risqué |
| Intermediate ou mart existant | Exit 2 sans `--force` | Ne jamais écraser du travail manuel en silence |
| Construction non convertible | Fragment recopié, `-- TODO` avec la raison, exit 1 | Un outil honnête vaut mieux qu'un outil qui devine |
| Codes de sortie | 0 : converti sans TODO. 1 : converti avec TODO, ou `check` signale une erreur. 2 : entrée invalide, mapping manquant ou conflit de fichiers | Cohérent avec `check` |
| Modernisation | Transformations sqlglot sur l'arbre (dont `eliminate_join_marks` si le spike la valide) *(à confirmer)* | Réécriture fiable et non textuelle |
| Mise en forme du SQL généré | `sqlglot` `pretty=True`, dialecte Oracle, mots-clés en minuscules *(à confirmer)* | Sortie stable, donc testable par comparaison de texte |
| Modules | `src/dbtidy/bin/convert/` (analyse, modernisation, génération, écriture) | Convention du projet : le code métier va dans `bin/` |
| Oracle Free | Étape séparée, test marqué `oracle`, ignoré par défaut et en CI | Lourd (Docker), non requis pour les tests de structure |

## Critères d'acceptation

- [ ] Le spike (`docs/spikes/convert_split.py`) convertit 3 requêtes, et ses conclusions sont reportées dans cette spec (décisions *(à confirmer)* tranchées).
- [ ] `validate-config` accepte une section `convert.sources` valide et rejette une section invalide (exit 2).
- [ ] Sur une requête à deux tables jointes avec `NVL` et `GROUP BY`, `convert` écrit `_<source>__sources.yml`, deux `stg_`, un `int_` et un `fct_` dans les bons dossiers.
- [ ] Le top N imbriqué devient `FETCH FIRST` ; `ROWNUM` et `ORDER BY` dans le même `SELECT` produisent un `-- TODO`.
- [ ] `SUM(x) AS total` et `RANK() OVER (ORDER BY SUM(x))` de la requête principale sont dans le mart.
- [ ] Une auto-jointure produit un seul staging avec l'union des colonnes.
- [ ] Sortent en 2 : colonne sans préfixe dans une jointure, `SELECT *`, sous-requête du `FROM` sans alias, collision de noms dans une conversion, nom trop long, `--name` sans préfixe mart, staging existant sans les colonnes requises.
- [ ] Les modèles générés ne contiennent plus de `(+)`, `NVL` ni `DECODE`.
- [ ] Chaque ligne du tableau « Règles de découpage » et chaque cas limite a un test qui vérifie la couche du modèle produit.
- [ ] Un staging généré ne contient ni `WHERE`, ni alias, ni expression : seulement des colonnes.
- [ ] Un `GROUP BY` dans une CTE reste dans son `int_`, et un `GROUP BY` de la requête principale va dans le mart.
- [ ] Chaque CTE de la requête donne un modèle `int_` référencé par `ref()`.
- [ ] Chaque modèle généré est relu par sqlglot sans erreur, et `check` ne remonte aucune erreur sur les modèles sans `-- TODO`.
- [ ] Une requête avec `CONNECT BY`, `UNION` ou une sous-requête corrélée produit un `-- TODO` explicite et sort en 1.
- [ ] Un fichier PL/SQL ou `MERGE` et un schéma absent du mapping sortent en 2 avec un message en français.
- [ ] Un staging existant est réutilisé sans être modifié. Un intermediate ou un mart existant bloque sans `--force` et est remplacé avec.
- [ ] `--dry-run` n'écrit aucun fichier.
- [ ] `--rename t1=clients_actifs` produit `int_clients_actifs.sql` et les `ref()` qui pointent dessus ; un `ANCIEN` inconnu sort en 2.
- [ ] Les 10 requêtes de `examples/legacy/` sont converties et leurs résultats testés.
- [ ] Sur Oracle Free, l'ancienne requête et les modèles générés donnent les mêmes lignes pour les 10 requêtes.
- [ ] La doc Sphinx décrit `convert`, se construit sans warning, et `CHANGELOG.md` décrit la 0.3.0.
