# Spec — v0.2 : conventions en YAML et publication PyPI

*Rédigé le : 7 octobre 2026*

## Contexte

La v0.1 fournit `dbtidy check` avec 5 règles (STG001-004, ORA001). Les préfixes de couche sont codés en dur dans `layers.py`, toutes les violations font échouer la commande et l'outil ne s'installe que depuis le dépôt. La feuille de route ([roadmap-sql-oracle-dbt.md](roadmap-sql-oracle-dbt.md), section v0.2) fixe le contenu de cette version.

## Objectif

Rendre `dbtidy` utilisable par n'importe quelle équipe grâce à un fichier de conventions YAML (couches, préfixes, règles et sévérités), ajouter les règles Oracle et de nommage, puis publier `0.2.0` sur PyPI.

## Périmètre

- Fichier `dbtidy.yml` validé par `pydantic` :
  - couches `staging`, `intermediate`, `mart` avec leur dossier et leurs préfixes ;
  - casse attendue des colonnes ;
  - longueur maximale des identifiants Oracle ;
  - sévérité de chaque règle : `error`, `warning` ou `off`.
- Sévérité : seul un `error` fait échouer `check` (exit 1). Un `warning` s'affiche mais sort en 0.
- Nouvelles règles Oracle :
  - ORA002 : `NVL` → `COALESCE` ;
  - ORA003 : `DECODE` → `CASE` ;
  - ORA004 : comparaison `= ''` ou `<> ''`, toujours fausse ou nulle en Oracle ;
  - ORA005 : identifiant trop long.
- Règles de nommage pilotées par la configuration :
  - NAM001 : le préfixe du fichier ne correspond pas au dossier de sa couche ;
  - NAM002 : la casse d'un alias de colonne ne correspond pas à la convention.
- Option `check --config PATH`. Sans cette option, `dbtidy.yml` est cherché dans le répertoire courant. S'il est absent, les valeurs par défaut s'appliquent et reproduisent le comportement de la v0.1.
- Commande `dbtidy validate-config [PATH]`.
- Hook pre-commit prêt à l'emploi (`.pre-commit-hooks.yaml`).
- Documentation Sphinx (configuration, règles), publiée sur GitHub Pages.
- `CHANGELOG.md`.
- Publication de `0.2.0` sur PyPI.

## Hors périmètre

- Règles candidates issues de `dbt-project-evaluator` : pas de `source()` hors staging, `schema.table` en dur, trop de jointures. Elles sont reportées à une 0.2.x.
- Couches personnalisées au-delà de `staging`, `intermediate` et `mart`.
- Configuration lue dans `dbt_project.yml` ou `pyproject.toml`.
- Passage à `typer` ou `rich` : argparse et la sortie texte suffisent.
- `noqa` au niveau du fichier.

## Décisions

| Sujet | Décision | Raison |
| --- | --- | --- |
| Nom et recherche du fichier | `dbtidy.yml`, cherché dans le répertoire courant, ou `--config PATH` | Simple et explicite, sans remonter l'arborescence |
| Absence de fichier | Les valeurs par défaut reproduisent la v0.1 (préfixes `stg_`, `int_`, `fct_`, `dim_`) | Pas de régression, l'outil marche sans configuration |
| Préfixes | `prefixes: [fct_, dim_]` (liste) au lieu de `prefix: stg_` | Une couche mart a plusieurs préfixes |
| Chemins des couches | Relatifs au dossier du fichier de configuration | Résultat indépendant du répertoire d'où l'on lance la commande |
| Classification | Le préfixe reste le critère, le dossier ne sert qu'à NAM001 | Décision v0.1 conservée |
| Clés inconnues | Erreur de validation (`extra="forbid"`), y compris un code de règle inconnu | Une faute de frappe ne doit pas désactiver une règle en silence |
| Configuration invalide | `check` et `validate-config` sortent en 2 avec la clé fautive et la raison | Principe « 2 = erreur de configuration » de la feuille de route |
| Sévérités par défaut | `error` : STG001-004, ORA001, ORA004, NAM001. `warning` : ORA002, ORA003, ORA005. `off` : NAM002 | NVL et DECODE marchent mais sont à moderniser, et la casse dépend de l'équipe |
| Longueur des identifiants | `oracle.max_identifier_length: 30` par défaut | Le legacy visé est souvent en compatibilité 30 caractères ; 128 si Oracle ≥ 12.2 |
| Noms factices Jinja | Exclus d'ORA005 | `source__erp__clients` est un artefact de la substitution, pas un identifiant du projet |
| Dépendances | `pydantic` et `pyyaml` (avec `types-PyYAML` en dev) | Choix de la feuille de route |
| CLI | On reste sur argparse | Déjà en place, pas de dépendance de plus |
| Sortie | Texte `chemin:ligne: CODE [warning] message`, JSON avec un champ `severity` | La sévérité est visible sans changer le format v0.1 pour les erreurs |
| Publication | `uv build` en local, puis workflow GitHub de *trusted publishing* déclenché par un tag `v0.2.0` | Pas de jeton PyPI stocké ; le push et le tag restent des actions humaines |

## Critères d'acceptation

- [ ] Sans `dbtidy.yml`, `check` sur `examples/jaffle_shop_oracle` ne lève aucune violation de plus qu'en v0.1, hors les nouveaux warnings ORA002 et ORA003.
- [ ] Un `dbtidy.yml` invalide (clé inconnue, sévérité inconnue, code de règle inconnu) donne un message localisé et exit 2, pour `check` comme pour `validate-config`.
- [ ] `validate-config` sur un fichier valide sort en 0.
- [ ] Une règle en `off` n'apparaît plus. Une règle en `warning` apparaît sans faire échouer la commande (exit 0 si elle est seule).
- [ ] Un préfixe défini dans la configuration (par exemple `src_` pour staging) déclenche les règles STG.
- [ ] ORA002 à ORA005, NAM001 et NAM002 ont chacune au moins un cas conforme et un cas en violation testés.
- [ ] Deux configurations différentes donnent deux résultats différents sur `examples/jaffle_shop_oracle`, et cette différence est testée.
- [ ] Le hook pre-commit `dbtidy` fonctionne dans un dépôt de test (`pre-commit try-repo`).
- [ ] La documentation Sphinx se construit sans warning et décrit la configuration et toutes les règles.
- [ ] `CHANGELOG.md` décrit la 0.2.0.
- [ ] `pip install dbtidy` installe la `0.2.0` depuis PyPI et `dbtidy --version` affiche `0.2.0`.
