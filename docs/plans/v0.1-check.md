# Plan — v0.1 : `check`, premières règles

*Rédigé le : 7 octobre 2026*
*Référence : [roadmap-sql-oracle-dbt.md](../specs/roadmap-sql-oracle-dbt.md), [phase-0-fondations.md](phase-0-fondations.md)*

## Objectif

Une commande `check` qui analyse les modèles d'un projet dbt et bloque la CI si l'architecture n'est pas respectée. Durée indicative : 4 à 6 semaines.

## Prérequis

- Phase 0 terminée : `sqlglot` validé sur du SQL Oracle, parsing Jinja validé, dépôt + CI en place.
- Toutes les règles sont de sévérité `error` par défaut en v0.1 (pas de configuration de sévérité avant v0.2) : toute violation fait échouer la commande (exit 1). *Remplacé en v0.2 : sévérités configurables dans `dbtidy.yml`, ORA002/ORA003 en `warning` par défaut ([v0.2-config-pypi.md](v0.2-config-pypi.md)).*

## Règles de départ

| Code | Règle | Exemple détecté |
| --- | --- | --- |
| STG001 | Un modèle staging ne lit qu'une seule source | Deux `source()` dans le même modèle |
| STG002 | Pas de jointure dans le staging | `JOIN` ou jointure `(+)` |
| STG003 | Pas d'agrégation dans le staging | `GROUP BY`, `SUM`, `COUNT`, `DISTINCT` |
| STG004 | Le staging lit une source, pas un autre modèle | `ref('stg_...')` dans un staging |
| ORA001 | Jointure Oracle `(+)` détectée (toutes couches) | `a.id = b.id(+)` → suggérer `LEFT JOIN` |

- [x] Remplacer les appels Jinja `ref()`/`source()` par des noms factices de même longueur, avec une table de correspondance (nom factice → nom réel + type).
- [x] Parser le SQL obtenu avec `sqlglot` (dialecte `oracle`).
- [x] Implémenter STG001 : compter les `source()` distincts dans un modèle staging.
- [x] Implémenter STG002 : détecter toute clause `JOIN` ou jointure `(+)` dans un modèle staging.
- [x] Implémenter STG003 : détecter `GROUP BY`, `SUM`, `COUNT`, `DISTINCT` dans un modèle staging.
- [x] Implémenter STG004 : détecter un `ref()` vers un modèle préfixé `stg_` (ou autre) dans un modèle staging.
- [x] Implémenter ORA001 : détecter la syntaxe `(+)` dans n'importe quelle couche, message suggérant `LEFT JOIN`.
- [x] Afficher chaque violation : fichier, ligne, code, message en français, piste de correction.
- [x] Option `--json` pour la sortie CI.
- [x] Option `-- noqa: CODE` sur la ligne concernée pour désactiver une règle ponctuellement (convention `sqlfluff`, décidée en amont).
- [x] Codes de sortie : `0` conforme, `1` violation, `2` erreur de configuration/parsing.
- [x] Écrire les tests : un cas conforme + un cas en violation pour chacune des 5 règles (10 tests minimum).
- [x] Préparer un jeu de données `jaffle_shop` réécrit en style Oracle legacy (au moins les jointures `(+)`) pour valider `check` en conditions réalistes.
- [x] Rédiger le README avec un exemple de sortie de `check`.
